# Track 6 — Space Logistics and the Research Frame

## 1. Orientation

This track exists so that the project's eventual novelty claim survives contact with people who already know this field cold: Prof. Rathinam, and any reviewer who reads the related-work section of a future paper. The project is an open-source, satvis-quality 3D satellite/orbit visualization platform that will grow an interplanetary trajectory-optimization layer (Lambert/porkchop in Phase B, then multi-objective route search with EMOA* in Phase C). Track 6 asks: what does the *adjacent* academic and applied field already do, and where exactly does this project sit relative to it?

Four communities turned out to matter. First, the Georgia Tech / MIT "space logistics as network flow" school (Koki Ho and collaborators), which solves whole-campaign logistics as single-objective LP/MILP/MINLP problems on time-expanded networks. Second, applied tools built for mission designers, exemplified by NASA's Trajectory Browser, which is the closest existing public analogue to this project's planned Phase C porkchop layer. Third, the Global Trajectory Optimisation Competition (GTOC), the field's benchmark for expert-level combinatorial-plus-continuous trajectory optimization, and the reason the astrodynamics toolbox `pykep` exists at all. Fourth, the real, currently-unsettled engineering problem of Starship HLS propellant-depot logistics, which supplies concrete, dated, disputed numbers that make the novelty claim land as more than an academic thought experiment. A fifth section collects sourced cislunar delta-v/time-of-flight numbers that Phase B/C can use as starter edge weights instead of inventing figures.

Mapped to project phases: this track's findings mainly inform Phase C's graph-construction methodology (how to build a tractable time-expanded or event-driven network for EMOA* to search) and the professor-facing scouting-report deliverable (why this project is not simply redoing GT/Koki Ho's MILP work, and not simply redoing NASA's porkchop tool). It also feeds the tool-paper-vs-benchmark-paper-vs-methods-paper publication strategy question that recurs across all three track questions below.

A verification pass (two independent lenses: "compute," which re-derived and re-read primary sources directly, and "source," which re-checked citations independently) was run against the five most load-bearing claims from the original reader notes. ## 3. Core notes

### 3.1 The Georgia Tech / MIT space-logistics-as-network-flow school

Koki Ho's line (PhD under Olivier de Weck at MIT, now runs the Space Systems Optimization Group at Georgia Tech) treats a whole space campaign — not a single trajectory — as a **network flow problem**. The lineage: Taylor et al. (integer-programming, time-expanded, ~6 static nodes, computationally limited) → Ho, de Weck, Hoffman, Shishko 2014 (time-expanded networks, LP-based) → Ishimatsu et al. 2016 (generalized multi-commodity network flow, GMCNF) → Jagannatha & Ho 2020 (event-driven networks, genuine MILP) → Chen & Ho 2018 and later group papers folding in spacecraft design (MINLP) and depot/servicing siting (2022-2026).

**Core formulation (Ishimatsu et al. 2016, read in full).** Nodes N are physical locations, some reused across time; node $i$ carries a supply/demand value $b_i$ ($b_i>0$ = source, $b_i<0$ = sink, $b_i=0$ = transshipment). Arcs $A \subset N \times N$ represent every physically possible move — a chemical burn, aerocapture, nuclear-thermal burn, ISRU step, crew consumption, propellant boil-off — and the model is a **multigraph**: parallel arcs between the same two nodes represent competing technology choices (LOX/LH2 vs. NTR vs. aerocapture), and self-loops represent waiting or in-place ISRU processing. Each arc $(i,j)$ carries a generalized flow multiplier $\mu_{ij}$, not just a per-unit cost $c_{ij}$: an arc can consume or generate flow (a burn consumes propellant mass; ISRU generates it). The full GMCNF formulation attaches an A/B/C matrix system per arc — A for flow-equilibrium (conservation), B for flow-transformation (how commodities convert into each other along that arc, e.g., propellant + inert mass → burned propellant + delivered payload), letting propellant, crew, cargo, and ISRU products all interact on the same arc.

The base problem is
$$\min J = \sum_{(i,j)\in A} c_{ij}\, x_{ij} \quad \text{s.t. generalized flow conservation at every node}, \quad 0 \le x_{ij} \le u_{ij}.$$

**Verified via independent re-read during verification (see ledger, item 1):** because technology trades are represented as parallel arcs rather than binary decisions, Ishimatsu et al.'s GMCNF model is solved as a **pure linear program**, not a MILP. Direct quote from the primary source: "because of its linear structure, this model can be formulated as a linear programming (LP) problem. One advantage of the LP formulation is that it can be quickly solved and that if solved, the solution is guaranteed to be optimal. This advantage of LP allows a large number of runs without much computational effort, which is more difficult in Taylor's integer programming (IP) formulation." A full-text search of the paper for "integer/binary/MILP" turns up no such variables anywhere in the GMCNF model itself — only in descriptions of the *prior* work (Taylor's IP formulation) that GMCNF was built to avoid. This is a real, checkable nuance: not every paper in this school is MILP.

**Objective and case study.** They minimize a single objective, **TLMLEO** (total launch mass to LEO, a campaign-spanning variant of IMLEO), and explicitly note — verified verbatim during the verification pass — that "the resulting strategy must be evaluated from multiple perspectives or the problem must be formulated as a multi-objective optimization. For the purpose of demonstrating GMCNF, however, this paper focuses on TLMLEO as a single-objective." **Correction from verification:** this sentence is a scope-limiting caveat in the case-study/methodology section, not part of the paper's formally labeled Future Work paragraph (which names only three items: risk/stochastic uncertainty, model linearity, and time-evolution of network topology, plus application-scope extensions). The paper never uses the word "Pareto." So: "single-objective is present capability, multi-objective is disclaimed as needed-but-out-of-scope" is verified; "explicitly designated as future work" overstates what the paper's own Future Work section contains. This is a minor wording correction but matters for precision when quoting the paper to the professor.

**Problem size and solver (verified, read directly, cross-checked twice during verification).** The Earth-Moon-Mars case study network has **16 nodes and 598 arcs (including 20 self-loops)** — confirmed independently by counting the 16 distinct node labels in the extracted text (KSC, PAC, LEO, GTO, GEO, LSP, LLO, EML1, EML2, EML4/5, DCO, DEIM, PCO, PHOB, LMO, GC) and by two separate quotes in the paper's Section III and Figure 5 caption. Solved in **MATLAB 8.3 (R2014a) with CPLEX 12.6** on an Intel Core i7-2640M @ 2.8 GHz: **~12 s preprocessing + ~1.2 s optimization** per run for baseline TLMLEO minimization — both figures confirmed verbatim during verification. Cheap enough to re-run dozens of times across sensitivity sweeps.

**Event-driven refinement (Jagannatha & Ho 2020, WebFetch summary only — "likely," not independently re-extracted).** Their motivation is exactly the "explosion" question this track cares about: a fixed-time-step network needs a node for every (location, timestep) pair even though most timesteps carry no feasible transfer — this is why Taylor's original time-expanded IP formulation could only handle a 2-week, 6-static-node lunar sortie. Their fix: nodes = mission events (launch/arrival opportunities, refueling ops), not uniform calendar days, and the network is built only over feasible transfer windows. This is a genuine **MILP**: binary variables select which vehicle/arc is used, continuous variables carry flow, and it couples high-thrust and low-thrust spacecraft in one network — the hard part being that a low-thrust arc's time-of-flight and deliverable-mass fraction are themselves functions of payload mass. Case study: cislunar propellant supply chain, solved with CPLEX; "hundreds of nodes, thousands of arcs, tens of thousands of binaries," minutes-to-hours solve times — these exact figures are **likely**, not verified (WebFetch's summarizer, not a direct pypdf read).

**2022-2026 group direction and the corrected multi-objective status (this is the single most important correction from verification — see Section 5, ledger item 2).** The original reader notes concluded that "none of the identified 2022-2026 group papers indicate a shift toward exact multi-objective Pareto-frontier search," treating this as supporting evidence that the whole school remains scalar/single-objective. **Verification found this is now stale.** Gollins, Grieser & Ho, "Multi-Objective Optimization of Space Exploration Campaign Schedules with Stochastic Launch Delay," *J. Spacecraft and Rockets* 63(3):751-769, 2026, DOI 10.2514/1.A36412 — confirmed via Crossref and Semantic Scholar DOI lookups during verification — presents a genuinely multi-objective framework: an exact multi-objective mixed-integer quadratically-constrained program (MOMIQCP) for small instances, trading cost vs. schedule robustness, plus an approximate "noisy multi-objective evolutionary algorithm (NMOEA)" for problems too large for the exact formulation. Koki Ho is thanked by name in Ishimatsu et al. 2016's acknowledgments, establishing direct lineage. **What survives:** this 2026 work is evolutionary/approximate at scale, not exact Pareto-front graph search over the GMCNF network-flow model itself, and grep of the GT SSOG publications listing found no paper extending GMCNF into exact Pareto-front graph search. So the EMOA*-based differentiator — exact, provably-complete multi-objective search over a graph, contrasted against MILP-with-scalarized-objective or evolutionary-approximate multi-objective search — still holds, but it must now be phrased more precisely: novelty is claimed over *exact/graph-search* Pareto optimization, not over "multi-objective optimization" broadly, since the latter is no longer true of the GT school as of 2026.

### 3.2 NASA Trajectory Browser: query model as UX research

NASA Ames Trajectory Browser (trajbrowser.arc.nasa.gov) is built for pre-Phase-A mission scoping: given a target body, it searches a precomputed database of impulsive Earth-departure trajectories and returns candidates meeting a user's launch-window/duration/delta-v budget. It is the closest existing public analogue to this project's planned Phase C.

**Query model.** Target-body selection is either (a) a NEO/asteroid filter by max absolute magnitude and Orbit Condition Code (0-9, positional uncertainty), or (b) a custom list of named bodies/planets. Trajectory constraints: mission type (one-way, round-trip, flyby, rendezvous); launch window as a coarse year range; max duration; max total $\Delta v$ in km/s, explicitly measured **"from a 200 km circular LEO"** — a good UX convention worth copying directly, since planners think in "budget from LEO," not raw $C_3$; and a single-objective toggle (minimize $\Delta v$ *or* duration, never both jointly). Result density options: "global optima," "1-yr local optima" (crude proxy exploiting near-annual/synodic repetition of Earth-body geometry), or "all trajectories." Hard cap of 100 results per query.

**Computation method (Foster, single-authored, see Section 5 ledger item 3 for the authorship correction).** Patched two-body/patched-conic approximation — only the Sun governs the heliocentric transfer leg; Earth's and the target body's gravity are reintroduced only at the endpoints. Lambert's problem is the core solver: for a fixed (launch date, transfer duration) pair, it gives the transfer orbit and hence both departure and arrival velocity vectors, from which $C_3$, injection $\Delta v$, and arrival $\Delta v$ follow directly. This is the exact Lambert-solver step this project's own Phase C is planned to build, confirming Lambert + patched-conic is the standard entry-level fidelity for pre-Phase-A tools, not a corner cut. Porkchop grid search is precomputed: (launch, arrival) dates are discretized with a step size of **roughly 5-16 days** depending on expected mission duration, Lambert's problem is solved at every grid point, and results are stored in a periodically-refreshed database — meaning launch/arrival dates in results are accurate only "to within a half time-step" of the grid. Ephemerides: JPL DE-421, with body state vectors sampled at **1-year intervals** from JPL HORIZONS (a fidelity limitation the guide itself flags near close encounters). Propulsion is strictly impulsive; no low-thrust modeling.

**Outputs.** Result rows carry: Route (itinerary shorthand), launch date, arrival date, time of flight, total $\Delta v$, injection $\Delta v$, arrival $\Delta v$, $C_3$, and DLA (declination of the launch asymptote — a nice real-launch-vehicle-constraint touch). It could not be confirmed whether the live results page links to a per-trajectory 3D viewer; the guide's prose covers methodology far more than the live UI, which appears to be JS-rendered and not capturable by WebFetch.

**Stated limitations (a checklist of what to improve on, per the guide):** patched two-body only (no perturbations, SRP, third-body effects); half-time-step date resolution; small bodies assumed zero-mass; coarse annual ephemeris sampling; single-objective per query only; 100-result cap; NEO orbit uncertainty surfaced but not risk-weighted into ranking.

**UX lessons for Phase C.** The query-form field set (target body, mission type, launch window, duration, $\Delta v$-from-a-named-reference-orbit, single-objective toggle) is a validated, minimal, field-tested input set — copy it, especially the $\Delta v$-from-LEO convention. The clearest novelty wedge is ranking: NASA's tool never computes a genuine joint Pareto front over $\Delta v$ and duration — it picks a single best point for one objective, buckets by "1-per-year" as a crude representative-optimum proxy, or dumps everything. A real Pareto-optimal set (EMOA*) replaces "pick $\Delta v$-optimal or duration-optimal" with "see the whole non-dominated tradeoff curve," including non-convex Pareto points a grid/weighted-sum approach can silently omit. An interactive 3D-linked version would add: click a point on the Pareto plot and see the actual 3D heliocentric arc render live; recompute on demand rather than serving a stale precomputed grid; a true joint multi-objective front instead of a single toggle; and surfacing non-convex Pareto-optimal solutions.

### 3.3 GTOC problem statements: what expert-level optimization looks like

GTOC is an invitation-only, roughly month-long, periodically-run (~every 1-2 years) competition organized by ESA's Advanced Concepts Team, pitting the world's best mission-design groups (JPL, Politecnico di Torino, Tsinghua, NUDT, ESA ACT, CNES, Moscow State) against one hand-crafted interplanetary trajectory problem. It is the field's benchmark for "expert-level" optimization, and it is the reason `pykep` exists — Dario Izzo built it at ESA ACT specifically as GTOC tooling; the current README still says the toolbox is used "from students and researchers to mission designers and competition participants (hello, GTOC!)."

**Five problem statements, verified from the GTOC portal:**

| Edition | Year | Name | Task | Winner |
|---|---|---|---|---|
| GTOC1 | 2005 | Save the Earth | Kinetic-impactor asteroid deflection, low-thrust; maximize orbital perturbation imparted | JPL (Petropoulos), via a Saturn gravity assist reversing the spacecraft's angular momentum before impact |
| GTOC5 | 2010 | Penetrators | Deliver penetrator probes to as many asteroids as possible via flyby after rendezvous-deployment of a main payload | JPL, low-thrust only |
| GTOC9 | 2017 | The Kessler Run | Remove 123 LEO debris objects via multi-target missions with maneuver/spacing/dwell constraints; minimize total mission cost | JPL (Petropoulos & Grebow), 4th GTOC win |
| GTOC11 | 2021 | Dyson Sphere | Build a 12-station Dyson ring via 10 spacecraft activating belt asteroids with low-thrust spirals | Tsinghua University & Shanghai Institute of Satellite Engineering (had placed last in GTOC1, won 16 years later) |
| GTOC12 | 2023 | Asteroid Mining | Fleet of low-thrust mining ships, 15-year horizon, mandatory Earth return; maximize mined mass delivered | JPL (Petropoulos & Lantoine) |

**GTOC9 detail (verified via primary problem statement, re-confirmed during verification pass).** Remove 123 debris objects; each mission chains impulsive rendezvous with $\le 5$ maneuvers between consecutive targets, $\le 30$-day inter-arrival spacing within a mission, $\ge 30$-day gap between missions, $\ge 5$-day proximity dwell at each target. Objective, confirmed verbatim from the official PDF (Izzo, ESA ACT, DOI 10.5281/zenodo.570193):
$$J = \sum_{i=1}^{n} C_i = \sum_{i=1}^{n} \left[ c_i + \alpha (m_{0i} - m_{dry})^2 \right], \quad \alpha = 2.0\times10^{-6}\ \text{MEUR/kg}^2$$
with a base mission cost $c_i$ that rises linearly over the competition window from 45 to 55 MEUR, plus a fixed penalty for each debris object left unaddressed of exactly **55.0018 MEUR** (not a round 55; "~55 MEUR" is accurate but slightly loose — these are two distinct 45-55-ish numbers and are worth keeping separate when writing this up). Spacecraft: 2000 kg dry, $\le 5000$ kg propellant, pericenter must stay above 6600 km.

**GTOC12 detail (verified via raw HTML fetch and leaderboard cross-check during verification).** Confirmed exactly: 35-ship submitted solution, 25,192.7 kg total collected mass (719.8 kg/ship, score 22,532.67 kg / 89.44%); post-competition refinement to 36 ships, 26,062.6 kg (724.0 kg/ship, score 21,904.51 kg / 84.05% — the lower percentage reflects the weighting formula, not a worse raw result). Cross-checked independently against the official GTOC12 Final Leaderboard (35-ship entry, score 22,532.672, Rank 1, Jet Propulsion Laboratory).

**Full winners table 2005-2025 (verified).** JPL, Politecnico di Torino, and — in the last decade — Tsinghua dominate, exactly the three schools named in the assignment; NUDT, Moscow State, CNES, and ESA ACT/JAXA also won individual editions.

**How winning teams solve these (inferred/likely, not from a directly-read JPL methods paper).** The recurring architecture is a two-layer decomposition: a combinatorial outer layer (tree search, branch-and-bound, beam search, or genetic/ant-colony metaheuristics) searching over which bodies to visit, in what order, partitioned across how many spacecraft; and a continuous inner layer solving the local optimal-control problem per leg (Lambert arcs for impulsive transfers, Sims-Flanagan or pseudospectral collocation for low-thrust) to price that edge's true cost. Because evaluating the inner layer exactly for every candidate sequence is too expensive, teams build cheap analytic or ML surrogate cost estimators to prune the outer search — directly verified in one case: arXiv:2004.02225 built a J2-nodal-drift-exploiting analytic $\Delta v$ approximation for LEO debris-to-debris transfers explicitly to let a combinatorial search evaluate many candidate mission orderings quickly, validated against JPL's GTOC9-winning solution. This is the textbook edge-cost-surrogate pattern this project would need for a large logistics graph.

Crucially, GTOC problems almost always collapse multiple sub-objectives into **one scalar competition score defined by the organizers** — GTOC9's $J$ folds cost and unremoved-debris penalty into one number; GTOC11 folds asteroids-activated and propellant-used into "a scoring formula" whose exact form was not located this session. This is worth stating explicitly as the contrast point: GTOC scores are scalarized for ranking purposes; this project's EMOA* approach is deliberately non-scalarizing.

### 3.4 Starship HLS refueling and depot logistics: why depot routing is real now

**The core fact.** Starship's Human Landing System cannot reach the Moon on the propellant it carries to orbit — Starship burns essentially all its propellant just reaching LEO. NASA's Artemis III/IV architecture therefore requires: a Starship propellant depot launched to LEO first; a series of uncrewed tanker Starships that launch, rendezvous, dock, and transfer LOX/methane into the depot; and the crewed HLS Starship launching last, topping off from the full depot, then departing for lunar NRHO rendezvous with Orion. This "aggregate propellant in orbit before departure" architecture is what makes multi-tanker scheduling a live engineering problem.

**Primary-source numbers (re-verified during the verification pass by downloading and pypdf-extracting the OIG PDF directly — successfully, contrary to the original notes' claim that this could not be done).** NASA OIG report **IG-26-004**, "NASA's Management of the Human Landing System Contracts," published **March 10, 2026**, states verbatim (p.5): "SpaceX will launch the Starship storage depot to low Earth orbit, which will be followed by **more than 10 Starship tankers** carrying propellant... Propellant aggregation begins **more than 200 days** prior to crew launching to allow for sufficient schedule margin. SpaceX is targeting to launch **one tanker flight every 6 days** until sufficient propellant is aggregated." **Correction from verification:** no "10-to-20" range appears anywhere in the primary document — a full-text grep for that phrasing returns zero matches. The 10-to-20 figure comes only from secondary journalism (Spaceflight Now's paraphrase) and should be cited as such, not attributed to the OIG report itself; the report's own stated floor is simply "more than 10."

For historical context, the tanker-count estimate has moved over time and across sources: Musk (Twitter, Aug 2021) estimated 4-8; GAO (2021) estimated 16 launches overall; a NASA official (2023) said "high teens"; SpaceX's own NASA bid documentation used 14; a SpaceX VP (2024) said "10-ish"; NASA OIG (March 2026) says "more than 10." SpaceX's own public estimates have stayed low and gotten more conservative over time; NASA/GAO/OIG estimates have consistently run higher.

**Propellant-transfer demo status — corrected during verification.** The original notes stated the ship-to-ship demo was "delayed 12 months to March 2026... expected to slip again to late 2026," implying the transfer demo itself was slipping to late 2026. **The primary source, read directly, shows this conflates two separate milestones.** Quote (p.14): "starting with Starship's next major milestone — a large-scale, vehicle-to-vehicle cryogenic propellant transfer test. This test was planned for March 2025 but has been delayed 12 months to March 2026." A separate sentence, about a *later*, *different* milestone: "There is also limited time — 4 months — between CDR and the **uncrewed demonstration mission**, which is expected to slip to the end of 2026." It is the uncrewed lunar-surface demonstration landing — not the propellant-transfer test — that the OIG says is slipping to late 2026; the transfer test's OIG-stated target remains March 2026 (already a 12-month slip from its original date). Note also: the report also states Flight 3 (March 2024) already demonstrated a propellant transfer *between two tanks within a single Starship vehicle* — intra-vehicle, not vehicle-to-vehicle — so the genuinely new milestone (first true ship-to-ship transfer) remains unflown as of the report. The report also flags that "end-to-end propellant aggregation will not be fully flight tested" before crewed use, and that boil-off mitigation for SpaceX's cryogenic propellants is not yet publicly disclosed.

**Schedule and cost consequence.** Per SpaceNews' summary of IG-26-004: Starship HLS development is delayed at least 2 years; critical design review is now slated for August 2026; an uncrewed HLS demo landing is targeted for end of 2026; Artemis III's crewed landing (originally June 2027) is considered unlikely to hold. Cost growth under the fixed-price contract structure has stayed comparatively small: SpaceX's HLS contract cost has grown 6% (~\$253M); Blue Origin's has grown <1% (~\$13M) — schedule risk, not cost risk, is where this program is exposed.

**Blue Origin's Blue Moon / Cislunar Transporter — a contrast architecture.** Blue Origin's National Team (Blue Origin prime; Lockheed Martin, Draper, Boeing, Astrobotic, Honeybee Robotics partners) uses hydrogen/oxygen propellant, not methalox, and a structurally different approach: a Cislunar Transporter (Lockheed-built tug plus a separate tanker, both launched individually on New Glenn, docking in LEO) travels to *lunar orbit* and refuels the lander there — refueling at the Moon, not solely in LEO. Blue Origin claims a zero-boil-off, solar-powered cryogenic system (targeting ~20 K storage) as their answer to the boil-off problem SpaceX has not yet publicly solved. Per OIG IG-26-004, Blue Moon is running at least 8 months behind schedule, with roughly half of PDR action items still open as of August 2025.

**Why this makes depot routing a live problem, in one line:** two independent multi-billion-dollar programs, audited twice in 2024-2026, still cannot agree on how many launches it takes to fill one propellant depot (4 to 20+ across five years of sources), the technology to do a ship-to-ship transfer at all has not yet been flight-demonstrated, and the fill sequence will not be validated end-to-end before crewed use. Scheduling N tankers against a depot with boil-off, launch-cadence, and reliability constraints to hit a translunar departure window is an open, contested engineering problem, not a solved one — and structurally it is exactly the kind of vector-cost, time-expanded scheduling problem multi-objective graph search was built for (objectives: tanker count/cost, schedule risk/margin consumed, boil-off loss).

**Computed slack.** At the OIG's stated 6-day cadence, a 200-day fill window holds $200/6 \approx 33.3$ possible launch slots. Even the high end of a 10-20 tanker range consumes only $10\times6=60$ to $20\times6=120$ of those 200 days at ideal cadence — an 80-140 day margin, which is schedule reserve for weather scrubs, pad turnaround, and vehicle issues, i.e. this is a stochastic-reliability scheduling problem layered on top of a resource-aggregation deadline, not a pure shortest-path problem.

### 3.5 Cislunar delta-v/time-of-flight starter table

Built and cross-checked a sourced cislunar delta-v/TOF table from three NASA primary sources, with numbers re-verified via two independent pypdf extraction passes during the verification pass (script: `notes/T6_5_cislunar.py`; table: `notes/T6_5_cislunar_table.md`).

**Whitley & Martinez (2016), "Options for Staging Orbits in Cislunar Space" (verified, and cross-checked a third time during verification).** Compares 7 cislunar orbit families (LLO, PCO, Frozen, ELO, NRO — Near Rectilinear Orbit, their term, not yet "NRHO" — EM-L2 Halo, DRO) under a consistent Orion MPCV assumption (~1250 m/s total $\Delta v$ budget, 21-day crew-lifetime constraint).

| Transfer | One-way $\Delta v$ | One-way TOF | Round-trip total |
|---|---|---|---|
| TLI $\to$ NRO (polar, 21-day mission) | — | — | 840 m/s |
| TLI $\to$ NRO (polar, 60-day mission) | — | — | 751 m/s |
| LLO $\leftrightarrow$ NRO (polar) | 730 m/s | 0.5 days | 1461 m/s |
| LLO $\leftrightarrow$ NRO (equatorial / far-side) | 898 m/s | 0.5 days | 1795 m/s |
| TLI $\to$ EM-L2 halo (polar landing, 18-day) | — | — | 800 m/s |
| TLI $\to$ EM-L2 halo (equatorial, 31-day) | — | — | 750 m/s |

Confirmed independently in three separate places in the primary document (slide 7 body text, slide 8 table, slide 13 summary table). **A precision note from verification:** the underlying worked example behind the round-trip total 1461 m/s is slightly asymmetric — 731 m/s / 0.55-day one leg, 730 m/s / 0.5-day the other — so "each leg exactly 0.5 days, 730 m/s" is a rounding of that example, not two identical numbers. Also: stationkeeping strongly favors NRHO/EM-L2 (both <10 m/s/yr; NRHO measured average 2.6 m/s/yr) over LLO (50+ m/s/yr) or ELO (>300 m/s/yr) — an operational, not transfer-cost, reason NRHO/Gateway was chosen.

**Epoch-dependence — corrected during verification.** The original claim paired Whitley & Martinez's 730/898 m/s NRO numbers directly with Foster, Brandt & Pellegrino's epoch-dependence finding, implying the latter quantifies variability in the former's specific numbers. **Verification found these are two related but distinct results.** Foster, Brandt & Pellegrino (NTRS 20220014057) study rendezvous with the real, ephemeris-modeled **Gateway 9:2-resonant southward NRHO** (a specific orbit defined years after Whitley & Martinez's more generic "NRO" family), and only for a **polar** LLO case — no equatorial/far-side result. Their finding, quoted directly: "An epoch scan was performed for every revolution of the NRHO in a calendar year... the wide variation in the optimal solutions was unexpected... driven by the moon's latitudinal libration." No specific numeric $\Delta v$ range is given in the extended abstract (it is qualitative/plot-only). So: the epoch-dependence mechanism is real and confirmed, but it is a general property demonstrated on a different, more specific orbit than the one Whitley & Martinez's 730/898 m/s numbers describe — those two numbers should be treated as illustrative single-epoch snapshots for a generic NRO, not as validated, epoch-robust constants for the actual Gateway NRHO.

**McGuire et al. (2021), Gateway trajectory paper.** Three qualitatively distinct paths to NRHO, by TOF: **Direct TLI** (chemical, e.g. Orion): 3-5 days. **Ballistic Lunar Transfer (BLT)** (chemical): 120-180 days. **Low Thrust Spiral** (electric, e.g. CMV/PPE): 120-365 days, worked DRM-3 example gives 383 days total (319 thrusting + 64 coasting), trading time for ~40% more mass delivered to NRHO than direct chemical delivery on the same launch vehicle. Reference Gateway NRHO: L2-southern, 9:2 lunar-synodic resonance, mean perilune radius 3,366 km, mean apolune radius 71,100 km, period **6.56 days**.

**CAPSTONE (verified).** Actual flight took ~138 days from launch (2022-06-28) to lunar orbit insertion (2022-11-13) — near the long end of McGuire's 120-180-day BLT band. No delta-v breakdown was found for it (gap).

**Two-body cross-check computations (own script, `notes/T6_5_cislunar.py`).** From a 200 km circular LEO, a minimum-energy TLI burn (apogee = 384,400 km) costs **3131.3 m/s** with a 4.98-day one-way coast; a faster ~3-day transfer to the same radius (via Kepler's-equation root-find on semi-major axis) costs **3154.5 m/s**. A deliberately crude, scalar-only patched-conic LOI estimate into a 100 km circular LLO from the 3-day case gives roughly **693.8 m/s** — roughly consistent (about 15 to 30 percent low, as expected for a scalar-only patched-conic estimate) with commonly cited Apollo-era LOI figures (~0.8-1.0 km/s), but explicitly flagged as approximate (it ignores actual velocity-vector geometry). Two sanity checks: LLO period at 100 km computed as **117.8 min**, matching Whitley & Martinez's own "~2 hrs" LLO figure; treating the reported NRHO perilune/apolune radii as a naive two-body Moon-only ellipse gives a **7.46-day period vs. the true 6.56-day (CR3BP) period** — about 14% high, a good teaching point about why NRHO needs CR3BP tools, not patched conics, for real mission design.

**Formulas used:** vis-viva $v = \sqrt{\mu(2/r - 1/a)}$; Kepler's equation $M = E - e\sin E$ solved by Newton's method; plane-change $\Delta v_{pc} = 2v\sin(\Delta i/2)$ (cited explicitly by Whitley & Martinez for their plane-change rows).

## 4. Answers to the track questions

### Q1. How does the time-expanded-network formulation map onto EMOA*'s input, and where does it explode?

**The mapping.** The GT/MIT node = (location, time) / arc = ($\Delta v$, ToF, capacity) formulation maps onto EMOA*'s expected input — a graph of nodes with vector-valued edge costs, e.g. $[\Delta v, \text{ToF}]$ — almost directly for a **single agent's route**. What does not transfer is the multi-commodity flow machinery: GMCNF's per-arc A/B/C matrix system exists to let propellant, crew, cargo, and ISRU products interact within a single scalar-objective LP/MILP solve simultaneously across a whole fleet; EMOA* has no native notion of multi-commodity flow conservation, because it searches for one agent's Pareto-optimal path set. Practically, a graph reused as EMOA* input should carry commodities as bookkeeping on top of a single-vehicle routing graph (mass/propellant tracked as state, not as separate parallel graphs), not as literal per-commodity graph replication.

**Where it explodes.** Node/arc count in a naive **uniform-time-step** time-expanded network scales as $O(\text{locations} \times \text{time-resolution})$, multiplied again by commodity count if commodities are represented as parallel flow variables per arc (as MILP/GMCNF formulations do). This is exactly the failure mode that drove the school's own evolution: Taylor's original time-expanded IP formulation could only solve a 2-week, 6-static-node lunar sortie before becoming intractable, which is why Ishimatsu et al. moved to a pure LP and why Jagannatha & Ho replaced fixed daily time-steps with event-driven nodes.

**Back-of-envelope, Earth-Moon-Mars, daily resolution, 2-year horizon.** Independent computations by different readers converge on the same order of magnitude:

| Quantity | Value | How computed |
|---|---|---|
| Locations (representative) | 10-12 | LEO, GTO/GEO, EML1/2, lunar orbit, lunar surface, Mars transfer orbit, Mars orbit, Mars surface, Phobos/Deimos, etc. |
| Time steps | 730 days | 2-year horizon |
| **Time-expanded nodes** | **≈ 7,300-8,760** | locations $\times$ 730 |
| Sparse (transfer-window-pruned) arcs | **≈ 35,000-40,600** | ~3-4 feasible departures/node/day + 1 wait edge |
| Naive fully-connected-per-day upper bound | **≈ 96,000-2.6$\times10^7$** | shown only to illustrate why nobody builds this |
| With 3-5 commodities as parallel flow variables | **≈ 105,000-330,000** decision variables | the MILP/GMCNF-specific blow-up EMOA* does not have to carry |

**Ground truth for comparison.** Ishimatsu et al.'s *actual solved* network is **16 nodes, 598 arcs** — one to two orders of magnitude smaller than any naive daily-resolution estimate, achieved entirely by using event-based (real transfer-opportunity) nodes rather than a calendar grid. **This is the concrete, defensible rule for Phase C: the graph-builder must be event-driven, not daily-gridded, to stay tractable for EMOA*.**

### Q2. Crispest one-paragraph novelty claim

*(Incorporating the verification correction to the GT-school multi-objective status.)*

*Also incorporating the companion gap analysis (gap_statement.md): four single-author 2026 repositories already couple a single-objective Lambert porkchop grid to an interactive 3D solar-system view (chipi/orrery, kevinkicho/k-solar-system-navigator, abc000cool/porkchop-mission-planner, tamiralmas/Orbital-Simulation), so the novelty claim below rests on exact multi-objective graph search coupled to interactive 3D, not on porkchop-to-3D coupling as such.*

The Georgia Tech/MIT space-logistics school (Ho, Ishimatsu, Jagannatha, Gollins, et al.) formulates campaign-level, multi-commodity space logistics as network-flow LP/MILP/MINLP problems solved by commercial solvers; through 2016-2021 this was uniformly single-objective (TLMLEO or similar), with the earliest papers explicitly disclaiming true multi-objective treatment as needed-but-out-of-scope, and as of 2026 the school has added a genuinely multi-objective capability (Gollins, Grieser & Ho 2026: an exact MOMIQCP for small instances plus an approximate evolutionary algorithm for larger ones) — but that capability is evolutionary/approximate at scale, not exact graph-search Pareto-front enumeration, and it has not been folded into the GMCNF network-flow formulation itself. Porkchop-plot tools (NASA's Trajectory Browser) return a single $\Delta v$-optimal or duration-optimal trajectory from a periodically-precomputed, coarse Lambert grid, toggling between objectives rather than jointly optimizing them, and can silently miss non-convex Pareto-optimal solutions. This project instead builds an exact multi-objective graph search (EMOA*) over a time-expanded/event-driven interplanetary transfer network with vector edge costs ($\Delta v$, time-of-flight, ...), returning the full non-dominated Pareto-optimal frontier of routes in one search — provably complete, not approximate, and not requiring re-solves across scalar weightings — wrapped in an interactive 3D visualization letting a user explore that frontier directly. The two schools are complementary, not competing: this project deliberately stays scoped to single-agent trajectory/route selection rather than fleet-wide multi-commodity flow scheduling, which is a defensible scope boundary rather than an omission.

### Q3. Tool paper, benchmark paper, or methods paper — venue and timeline

Evidence converges strongly on **tool paper first, benchmark paper as a close companion, methods paper last/optional**. EMOA* itself is Rathinam's own already-published algorithm, so this project's genuine novel contribution is the *application domain* (space-logistics/interplanetary graphs as EMOA* input, built event-driven per the Q1 sizing analysis) plus the *interactive 3D visualization* — a systems/tool contribution, not a new algorithm. Attempting a methods paper first risks a reviewer correctly noting "this is just an application of existing EMOA*." NASA's own Trajectory Browser is direct proof that a tool paper with no novel algorithm at its core (Lambert + patched-conic, textbook methods) is a fully legitimate, citable, peer-reviewed contribution at a mainstream venue (Foster, IEEE Aerospace Conference 2013, sole author — confirmed during verification, see Section 5) — lowering the bar for what counts as a credible first publication.

Recommended venue order:

1. **SoCS (Symposium on Combinatorial Search)** — a short tool/demo paper introducing the graph-construction pipeline plus a released benchmark instance set (sized in the spirit of Ishimatsu's ~16-node/~600-arc network, scaled up). Matches Rathinam's own EMOA* publication venue, and SoCS explicitly wants new applied domains/benchmarks for multi-objective and heuristic search.
2. **JOSS (Journal of Open Source Software)** — for the software itself once it has tests/documentation/real users; gates on code quality and usability, not novelty, so targetable in parallel.
3. **AAS/AIAA Astrodynamics Specialist Conference** — for the astrodynamics-facing framing (interplanetary trajectory search + visualization, ideally with real cislunar numbers such as the NRHO/Gateway parameters in Section 3.5), once the interplanetary/Lambert-porkchop layer (Phase C) is working; complementary, not competing, with the tool paper.
4. **Acta Astronautica / J. Spacecraft and Rockets** — only if a genuine methods contribution emerges (e.g. a dominance-check speedup specific to time-expanded space-logistics graphs, or handling epoch-dependent/time-varying edge costs — a real open modeling gap per the LLO↔NRHO libration-dependence finding, Section 3.5). Not a v1 target.

A benchmark paper (SoCS or ICAPS data/benchmark track) is a natural second deliverable once several real instances exist (Earth-Moon, Earth-Moon-Mars, small asteroid tours); the Starship HLS finding that even the industry's own parameter estimates are unsettled (4 to 20+ tankers, boil-off unmodeled publicly) argues for a benchmark-generation-and-parameter-sweep framing rather than claiming to solve one "correct" real-world instance.

**Plausible timeline.** A SoCS short/demo paper draft is realistic **3-6 months after Phase C begins** (once the interplanetary Lambert/porkchop layer plus a first EMOA* integration exist), with JOSS submission targetable in parallel roughly 2-4 months after a working v1. This mirrors the field's own pattern: even GTOC's methods/results papers (e.g., the Acta Futura GTOC9 special issue) are published after a working competition result exists, not before.

## 6. Implications for the build

1. **Phase C graph construction must be event-driven, not daily-gridded.** The Q1 sizing comparison (naive daily-resolution: ~7,300-8,760 nodes / ~35,000-40,600 arcs vs. Ishimatsu's actual event-driven 16 nodes / 598 arcs) is the single most concrete, citable engineering rule from this track: build nodes only at real transfer-opportunity events (launch windows, arrival windows, feasible Lambert solutions), never on a uniform calendar grid. This is a direct, testable design constraint for the graph-builder module.

2. **Keep commodities as state, not as parallel graph copies.** EMOA*'s natural fit is single-agent, vector-cost route search. Do not replicate the GT school's per-commodity edge-variable architecture (which is what drives their MILP problem sizes into the 100,000s of decision variables) — track mass/propellant/crew consumption as accumulated state along a single-vehicle path instead. This is a genuine, defensible scope boundary, not a shortcut, and should be documented as such in any design doc or paper.

3. **Copy Trajectory Browser's $\Delta v$-from-a-named-reference-orbit convention.** Express $\Delta v$ budgets "from a 200 km circular LEO" (or equivalent) rather than raw $C_3$ — this is a validated UX pattern from a field-tested tool, not a guess.

4. **Build a joint Pareto-front UI as the explicit differentiator, not an afterthought.** Both Trajectory Browser (single-objective toggle) and the GT school's pre-2026 work (single scalarized objective, re-solved per scenario) lack this; it is the crispest, most defensible novelty wedge. Any Phase C demo should visibly show non-convex Pareto points that a weighted-sum approach would miss — this is a concrete oracle/test to build: construct at least one synthetic or real scenario with a known non-convex Pareto front and verify EMOA* recovers points a weighted-sum sweep does not.

5. **Test/oracle suggestion: two-body cross-checks as regression tests.** The T6.5 script's sanity checks (LLO period at 100 km ≈ 117.8 min matching Whitley & Martinez's "~2 hrs"; naive two-body NRHO period ≈ 7.46 days vs. true CR3BP 6.56 days, ~14% high) are good, cheap regression-test patterns: any orbital-mechanics utility function added to the codebase should ship with a known-answer check against a published number, exactly like this.

6. **Do not hard-code cislunar edge weights as epoch-independent constants.** The corrected Whitley & Martinez / Foster et al. finding (Section 3.5, ledger item 5) means any UI or graph that uses 730/898 m/s style numbers for LLO↔NRHO must either (a) disclose them as single-epoch illustrative values, or (b) implement actual epoch-scanning if precision matters for a demo — do not present them as validated, time-invariant constants.

7. **Pitfall: don't conflate LP and MILP when discussing "the GT/MILP school."** Ishimatsu et al.'s workhorse formulation is LP; only later work (Jagannatha & Ho's event-driven model, Chen & Ho's MINLP) is genuinely mixed-integer. Getting this backwards in front of the professor (an ME who may know these exact papers) is an avoidable, visible error.

8. **Pitfall: distinguish IMLEO from TLMLEO.** Ishimatsu et al. deliberately use TLMLEO (campaign-summed) rather than IMLEO (normally per-mission) — don't conflate the two when citing this work.

9. **Use realistic, sourced scenario parameters from the Starship HLS case (10+ tankers, ~6-day cadence, 200-day fill window) for a Phase C demo scenario** instead of inventing arbitrary numbers — this doubles as honest, citable content for a professor meeting or an application talking point.

10. **Fallback pattern worth remembering:** when WebSearch budget is exhausted, WebFetch against a domain's own citation-search API (NASA NTRS's `https://ntrs.nasa.gov/api/citations/search?q=...`) or a metadata API (Crossref's `https://api.crossref.org/works?query...`) works well and should be a standard fallback for future NASA-source-heavy or citation-heavy research tasks. Also: when WebFetch fails to extract a PDF's text, download the raw PDF and extract locally with the venv's `pypdf` — this succeeded on both the Ishimatsu 2016 paper and the NASA OIG IG-26-004 report during verification, where the original single-pass attempts had reported failure.

## 8. Glossary of credibility vocabulary encountered

- **verified** — the fact was read directly from a primary source (a paper's full text, an official competition page, a directly-executed script) by the agent reporting it, or independently computed and cross-checked.
- **likely** — the fact came from a secondary source (a summarizer's paraphrase of a PDF, a WebFetch summary rather than a direct extraction, a listing page rather than an opened abstract) or strong domain knowledge not independently re-checked against a primary text.
- **uncertain** — evidence is thin, contradictory, or a plausible inference without direct textual support.
- **confirmed** (verification-ledger verdict) — an independent re-check, using its own methodology, reproduced the original claim with no material correction needed.
- **needs_qualification** (verification-ledger verdict) — the claim's substance holds but requires a correction, missing caveat, or updated context (e.g., new evidence postdating the original claim) before it can be repeated as-is.
- **plausible** — used informally in some reader notes for an estimate built on reasonable but non-cited assumptions (e.g. an illustrative node-count calculation using an assumed location list).
- **primary source** — the actual paper, official competition page, or government report itself, as opposed to journalism or a summary about it.
- **secondary source** — journalism, a search-result snippet, or a fetch tool's own summarization of a document, standing in for a primary source that could not be opened directly.
- **gap** — a fact the assignment or track questions call for that no reader could locate or verify within the session's tool budget; explicitly listed rather than silently omitted.
- **"treat as X, not Y"** — a recurring phrase in these notes flagging that a claim's confidence level should not be silently upgraded (e.g., "treat as likely, not verified") when repeating it in a different context, such as a conversation with the professor.
